# Le Painterr

A 3D browser game about painting a house, built with Three.js and Vite. Pick a colour, drag the roller
across bare siding, and cover four walls and two gables before the clock gets interesting.

## Running it

```bash
npm ci
npm run dev
```

Production-equivalent deployment check:

```bash
GITHUB_ACTIONS=true GITHUB_REPOSITORY=<owner>/<repo> npm run build
GITHUB_ACTIONS=true GITHUB_REPOSITORY=<owner>/<repo> npm run smoke:deployment
```

The build is repository-relative: `vite.config.js` derives the Pages base from `GITHUB_REPOSITORY`, so
the same config works from a fork or after a rename without editing a hard-coded path.

## Controls

| Action | Input |
| --- | --- |
| Paint | Hold left mouse, or drag with one finger |
| Orbit | Right mouse drag, two-finger drag, arrow keys, or `A` / `D` |
| Height | `W` / `S` |
| Zoom | Mouse wheel, or `Q` / `E` |
| Colour | Number keys `1`–`6`, or click a swatch |

## How the painting works

Each paintable surface owns a 2D canvas that is uploaded as a `CanvasTexture` and blended over the siding
inside the standard material (`src/paintable-surface.js`). The siding is tiled through a shader uniform
rather than `map.repeat`, so the paint layer can share the mesh's untransformed UVs — one varying, no
second UV channel, and uniform texel density across differently sized walls.

Coverage is tracked in a coarse boolean grid updated as you paint, so the HUD never has to read pixels
back from the GPU. Window and door rectangles, and the corners outside the gable triangles, are excluded
from the denominator — otherwise 100% would be unreachable.

## Asset pipeline

**Every shipped texture is WebP. No PNG or JPEG ever reaches `dist/`.**

```
assets/source/*.png        lossless sources, git-ignored, procedurally regenerated
        ↓  npm run assets:optimize
assets/*.webp              committed, shipped, budgeted
        ↓  vite build
dist/assets/*-<hash>.webp  byte-identical to the committed WebP
```

| Command | What it does |
| --- | --- |
| `npm run assets:source` | Regenerates the lossless PNG sources into `assets/source/` |
| `npm run assets:optimize` | Regenerates sources, then re-encodes every WebP and checks budgets |
| `npm run assets:verify` | Checks the committed WebPs without rewriting them |
| `npm run smoke:deployment` | Checks the built `dist/`, including image budgets |

`assets/textures.manifest.json` is the single source of truth: dimensions, role, encode settings and a
per-image byte budget for every texture. Adding a texture to the game without a manifest entry fails the
smoke test, because an undeclared image has no budget.

Sources are generated by `scripts/generate-source-textures.mjs` rather than committed as binaries, which
keeps re-encoding reproducible from a clean checkout — same sources, same settings, same sharp version,
same bytes. To use hand-authored art instead, drop the PNG at the manifest's `source` path and remove the
matching generator from `GENERATORS`; the encode step is unchanged.

### Roles

| Role | Meaning |
| --- | --- |
| `color` | sRGB albedo, opaque. Lossy WebP is fine. |
| `data` | Linear non-colour data (roughness, masks). Encoded near-lossless so banding does not leak into lighting. |
| `cutout` | Has a real alpha channel and is sampled with `alphaTest`. |

**Cutouts encode at `alphaQuality: 100`.** Lossy alpha shows up as edge fringing on every silhouette the
renderer samples with `alphaTest` — the hedge foliage is the obvious victim here. The manifest loader
rejects a `cutout` entry with any other `alphaQuality`, and the optimizer pins it again at encode time.

### Budgets

Two budgets are enforced, both in `assets/textures.manifest.json`:

- `maxBytes` per texture, capped by the global `budgets.perImageBytes`
- `budgets.totalImageBytes` across every image in the build

`npm run smoke:deployment` asserts both against the files actually in `dist/`, so an oversized texture
fails the build rather than someone's data plan. It matches shipped files to manifest entries by content
hash, which also proves Vite shipped the optimizer's output untouched.

## Deployment

`.github/workflows/le-painterr-pages.yml` builds, verifies the textures, and runs the deployment smoke
test on every push and pull request that touches this directory.

GitHub Pages serves one site per repository, and Zen Driving at the repository root already owns this
one. Publishing Le Painterr is therefore a manual `workflow_dispatch` run that requires typing `yes` into
the `publish` input, so a push to `main` cannot replace the driving game by accident. Moving this
directory into its own repository makes the deploy job an ordinary push-triggered one — the base path
follows `GITHUB_REPOSITORY` automatically.
